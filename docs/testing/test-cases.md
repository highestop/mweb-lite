# Test cases

This catalog records behavior, test level, verification path, data source, and the latest recorded result. It contains 61 cases: 43 Swift tests, 5 preview-component integration cases, 12 full-app preview cases, and 1 release-app case. Follow the [test guide](test-guide.md) for setup, implementation, and evidence recording. A passing test verifies only its **Then** statement; it does not certify the whole feature. In particular, AppKit component tests and `PreviewTests.app` are integration tests, not full-application end-to-end tests.

## Format and result rules

Each case has a permanent ID and explicit **Given / When / Then (GWT)** statements. Keep IDs when renaming tests. Add a separate row when a scenario needs a different setup, test level, verification path, or result. Update the implementation, fixture, case, and evidence together when behavior changes.

| Field | Meaning |
| --- | --- |
| ID | Stable identifier used in logs and review discussions. |
| Given | Initial state and required data. |
| When | The action under test. |
| Then | Observable assertions that determine the result. |
| Level | `Unit`, `Integration`, or `End-to-end`. The level describes the test's scope independently of where or how it runs. |
| Path | `CI`, `Local script`, `Preview app`, or `Release app`. The path identifies the execution environment and application variant used to verify this row. |
| Data | Initial input source and any additional generated setup: `Inline` for literals/setup in test code, `Fixture: <source link>` for committed fixture inputs, or `Mixed: <source link> + <generated setup>` when both are required. Links identify source files/directories, not a mutable run copy. |
| Status | `Pending`, `CI passed`, `Local script passed`, `Preview app passed`, `Release app passed`, `Failed`, `Blocked`, or `Skipped`. |
| Verification | Exact automated selector, or full-app steps and fixture reference. |
| Evidence | A durable run-record reference, including the tested source/fixture revision, environment, result, and log or screenshot references. Use `—` before execution. |

A passing status must match the recorded Path and its evidence. `CI passed` requires the row's assertions to run successfully in CI; the same command passing locally is evidence for `Local script passed`, not a CI result. `Preview app passed` and `Release app passed` require completing the stated flow in the corresponding packaged app and checking every expected result. Keep independently maintained paths in separate cases when their setup or assertions differ. A lower-level or different-path result can be linked as supporting evidence, but cannot substitute for the row's required verification.

Starting an app, passing a build, or running a related lower-level test is insufficient. `Skipped` means an optional path was intentionally not exercised; `Blocked` means a required prerequisite prevented execution. A result applies to the revision recorded in its evidence, not automatically to later edits. Reset affected rows to `Pending` when their behavior, fixture, or verification changes.

Data describes the case's initial inputs. Runtime database materialization and copying a fixture into an isolated run do not turn a Fixture case into Inline or Mixed. Action inputs such as text typed in the app belong in When; they do not change a fixture-based case's Data label. Mixed is used when the setup adds separate generated inputs, such as PV-001's outside-file and symlink escape probes. Record the resulting run directory in evidence, keeping it separate from the committed source link.

Do not place generated databases, app bundles, screenshots, or logs in this catalog. Keep generated run artifacts in the ignored run directory; retain a small text run record with an accessible evidence reference when recording a pass. A local-only artifact path must be labeled local-only so a reviewer can distinguish recorded local evidence from downloadable CI evidence.
